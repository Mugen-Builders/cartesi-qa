Contracts v3

The important contract changes we had to model

Claim staging

  • Claims now move through UNSTAGED, STAGED, then ACCEPTED.
  • acceptClaim is a separate transaction after claimStagingPeriod.
  • Events include the machine Merkle root.

Foreclosure and withdrawal

  • Each app has a WithdrawalConfig.
  • The guardian can call foreclose().
  • After foreclosure: prove accounts-drive root, then withdraw accounts.

New surface

  • Per-app claim counters.
  • getLastFinalizedMachineMerkleRoot(app).
  • Quorum factory and quorum deployment support.
  • Version tags on contracts.

Mental model

Before: one line to finality. Now: staged finality plus emergency exit.

Before this PR

  • Application lifecycle was one enum: ENABLED, DISABLED, FAILED, INOPERABLE.
  • Authority/Quorum claims were mostly tracked as submit then accept.
  • No local model for post-foreclosure observation.
  • No withdrawal event table or withdrawal API.

Now

  • Operator intent is enabled. Health/lifecycle is status.
  • Authority/Quorum claims use SUBMITTED, STAGED, ACCEPTED.
  • Foreclosure is durable L1 state: foreclose_block.
  • EVM Reader keeps watching for drive-prove and withdrawals.
Emphasize that foreclosure is not the same as corruption. A normal foreclosed app has status FORECLOSED, not INOPERABLE. INOPERABLE is reserved for local mismatch or corruption.
Current architecture

Services still communicate through PostgreSQL, but more L1 state is explicit

The architecture did not become message-driven. The important change is that the DB schema now has explicit states for things that contracts v3 made visible or required.
Sequence diagram

Authority claim lifecycle: submit and stage together, accept later

Authority stages in the same transaction as submit, but finality still waits for acceptClaim. That is why the node needs a local CLAIM_STAGED state and staged_at_block.
Sequence diagram

Quorum claim lifecycle: votes stage one claim, accept later

In Quorum, a submitted claim is not always staged by our transaction. The node must watch events and getClaim state, and it must classify conflicting staged or accepted claims carefully.
State machine

Epoch status changed: staging and foreclosure are first-class

DB triggers enforce the important transitions. CLAIM_STAGED is valid for Authority and Quorum only. PRT still settles through Dave tournaments and skips staging.
Application lifecycle

Application state became two dimensions: operator intent and effective status

Before

One field tried to mean both "should this app run?" and "is this app healthy?" 

ApplicationState

ENABLED
DISABLED
FAILED
INOPERABLE

This made foreclosure difficult: L1 observation must continue even when normal execution stops.

Now

The node separates what the operator wants from what the system knows. 

enabled: true | false

status:
  OK
  FAILED
  INOPERABLE
  FORECLOSED

foreclose_block: 0 | L1 block

Normal foreclosure is enabled=true, status=FORECLOSED, and foreclose_block>0.

Say this slowly. This is a key review and ops concept. Foreclose block is the source of truth for the L1 boundary.
Service filters

After foreclosure, services do less normal work and more observation

Service
Normal app work
Foreclosed app behavior
EVM Reader
Scans inputs, outputs, epochs, and L1 state for enabled apps.
Records foreclosure, then scans drive-prove and withdrawal events.
Machine Manager / Advancer
enabled && status=OK && foreclose_block=0
Keeps a machine only while pre-foreclosure inputs are still undrained.
Validator
Computes proofs for processed epochs.
Skips epochs that cannot become accepted after the foreclosure block.
Claimer
Submit, stage, accept Authority/Quorum claims.
Does read-only reconciliation and marks impossible claims CLAIM_FORECLOSED.
PRT
Runs Dave tournament work for PRT apps.
Skips new tournament work and reports pre-foreclosure drain progress.
The key operational point: do not disable foreclosed apps automatically if you still need post-foreclosure observation.
EVM Reader

Block scanning now has a foreclosure-first plan

The order matters. Foreclosure is detected before building the scan plan, so later scanners use the marker in the same tick.
Sequence diagram

Foreclosure: stop normal progress, keep observing L1

The node writes foreclosure atomically with the scan cursor. If the app was already INOPERABLE, EVM Reader preserves that status.
Withdrawal lifecycle

Foreclosure adds a second lifecycle after normal claims stop

1

Deploy with config

Set guardian, account layout, accounts drive start, and output builder.

2

Guardian forecloses

foreclose() makes normal submit and accept paths revert.

3

Prove drive root

Anyone anchors the accounts-drive Merkle root from the last finalized machine state.

4

Users withdraw

Each account is proven once and emits a Withdrawal event.

5

Node indexes

EVM Reader stores withdrawals and JSON-RPC exposes them to clients.

The all-zero WithdrawalConfig means no foreclosure path. A partial config is dangerous and should fail validation.
The node does not build withdrawal outputs for users. The on-chain output builder does that during withdraw(). The node helps with indexing and local proof tooling.
Sequence diagram

Accounts-drive proof and withdrawal event indexing

The withdrawal scanner uses getNumberOfWithdrawals as a monotonic counter and scans exact transition blocks. This reduces log scan cost and makes restart behavior deterministic.
Data model

The schema now protects the lifecycle with constraints and triggers

Application table

  • enabled and status replace the overloaded state model.
  • claim_staging_period is cached from L1.
  • Withdrawal config is stored in five typed columns.
  • Foreclosure, drive-prove, and withdrawal scan cursors are persisted.

Epoch table

  • New CLAIM_STAGED status.
  • New CLAIM_FORECLOSED terminal state.
  • staged_at_block is required for staged claims.
  • DB trigger rejects invalid transitions.

Withdrawal table

  • Stores on-chain Withdrawal events.
  • Primary key: app plus account index.
  • Used by JSON-RPC and CLI read paths.
  • Cursor update and event storage happen together.
This is a review focus area. A bad state transition can create silent chain/DB disagreement, so the trigger logic matters.

New tools

The CLI now covers deploy, foreclosure, proof, withdrawal, and reads

Operator commands

cartesi-rollups-cli foreclose <app>
cartesi-rollups-cli prove-drive-root <app> --proof-file drive-root-proof.json
cartesi-rollups-cli withdraw <app> --proof-file account-proof.json
cartesi-rollups-cli read withdrawals <app> [account-index]

Deploy and contract support

  • deploy application accepts --claim-staging-period.
  • --withdrawal-config and --withdrawal-config-file are supported.
  • deploy quorum adds v3 Quorum deployment.
  • contract output shows v3 fields.
  • deposit erc20 helps the withdrawal lifecycle test path.
Mention that foreclose needs guardian signing. Prove and withdraw are permissionless, but still need a gas payer.
New binary

cartesi-rollups-machine-tool helps produce proof files

Replay accepted inputs

cartesi-rollups-machine-tool replay \
  --template applications/erc20-withdrawal-dapp \
  --application erc20-withdrawal-dapp \
  --to-epoch 3 \
  --store snapshots/accepted-epoch-3

Replays accepted inputs from the node database into a stored machine.

Generate withdrawal proofs

cartesi-rollups-machine-tool prove accounts-drive \
  --snapshot snapshots/accepted-epoch-3 \
  --account 0x... \
  --accounts-drive-start-index 0x... \
  --out-drive-root-proof drive-root-proof.json \
  --out-withdraw-proof account-proof.json

Produces the JSON files consumed by prove-drive-root and withdraw.

This is useful for the demo. It also gives QA a repeatable way to generate test fixtures for post-foreclosure behavior.

Ops checklist

Deploy only after configuration and data assumptions are explicit

Before deploy

  • Update factory addresses: InputBox, AuthorityFactory, QuorumFactory, ApplicationFactory, SelfHosted, DaveAppFactory.
  • Set CARTESI_CLAIMER_MAX_ACCEPT_ATTEMPTS if the default 5 is not right for the network.
  • Confirm guardian wallets and withdrawal config for apps that need foreclosure.
  • Confirm snapshot policy for apps that may need withdrawal proofs.

Data and rollout

  • This alpha branch changes migration 000001. Do not reuse a v2-alpha DB without a plan.
  • Check that JSON-RPC clients expect enabled and status.
  • Monitor FORECLOSED, FAILED, INOPERABLE, and claim staging states separately.
  • Have guardian and gas-payer accounts ready for emergency flows.
The highest-risk deployment mistake is mixing old contracts, old factory addresses, or old DB shape with the new node binary.
Keep this practical. Operations needs exact checks more than protocol theory.
Known risk points

Where bugs would hurt most

Chain/DB divergence

A missed ClaimStaged, ClaimAccepted, Foreclosure, or Withdrawal event can make local state lie.

Mitigation: counters, event scans, cursors, reconciliation reads.

Bad withdrawal config

Wrong guardian, drive layout, or output builder can block recovery.

Mitigation: all-or-nothing config, validation, tool output checks.

Gas spending loops

Repeated acceptClaim failures should not burn gas forever.

Mitigation: max accept attempts marks app FAILED.

PRT assumptions

PRT never goes through CLAIM_STAGED and cannot settle new tournament work after foreclosure.

Mitigation: consensus-aware filters and DB trigger rules.

This is a good place to ask reviewers to use the bug taxonomy mindset: L1 ingestion, state corruption, consensus, and dispute resolution.
